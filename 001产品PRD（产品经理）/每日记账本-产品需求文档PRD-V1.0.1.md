### 1.5 V1.0.1 版本修订说明（本版新增）

> 本版只做一件事：把 PG-09 从页面清单里的一行字，落成可开发、可验收的页面级需求。动机见 ACC-02 产品决策说明——免登录模式的账单只存在本机浏览器，清理缓存即丢失，账号体系是数据信任的兜底，越早交付越好。
>
> 登录方式按评审反馈收敛为**用户名 + 密码两个字段**：不做到达率不可控的验证码链路，也不要求填邮箱；注册与登录拆成同页两个按钮，用户不必猜"点这个到底是注册还是登录"。页面状态因此是 10 个。代价是没有邮箱就没有自助找回——本版「忘记密码」只作说明与导出兜底，绑定邮箱／手机号的找回链路排在 V1.1，作为已知风险记入第十一章。

| 修订项 | 变更前（V1.0 基线） | 变更后（V1.0.1） |
| --- | --- | --- |
| 登录页颗粒度 | PG-09 仅一行描述"邮箱验证码登录" | **新增 ACC-02 详细规则、ACC-04 登录态与注销、5.5 页面详设与状态表**（登录方式与注册入口已改，见下两行） |
| 交付时间 | 账号体系整体排在 V1.1（第7-10周） | **登录/注册页提前至 V1.0.1（第7周）**；多端全量双向同步仍留 V1.1 |
| 登录方式 | 未定义 | **用户名 + 密码**（用户名 3–20 位、大小写不敏感、全局唯一；密码 6–64 位，服务端加盐哈希存储，前端不持有密码） |
| 注册入口 | 与登录合成一个「登录 / 注册」按钮，首见邮箱静默建号 | **注册与登录拆成同页两个按钮**：【注册并备份】建号、【登录】只校验凭据。两个动作各有独立失败态，避免"想登录却打错用户名被静默建成新号" |
| 本机数据 | 仅提示"数据保存在本机" | 登录后**本机账单一键上云**，冲突按"保留双方、`updated_at` 新者为准"合并 |
| 埋点与指标 | EV-08 注册成功 | **新增 EV-11 表单提交（登录／注册分档）／EV-12 认证结果／EV-13 迁移结果，及认证转化率、注册重名失败率两项指标** |
| 外部依赖 | 后端与数据库方案 | **新增账号服务 `/api/v1/auth/*`（用户名唯一索引、密码 argon2/bcrypt 加盐哈希、注册与登录两个接口）；本版无邮件与短信依赖，发送服务随 V1.1 的绑定与找回一并评审** |

## 二、产品概述

### 2.1 产品背景

日常生活中，很多人存在"钱不知道花到哪里去了"的困扰。电子支付普及后，消费变得无感化，个人更需要通过主动记录来建立对财务状况的感知。本产品旨在提供一个**简单、快速、无负担**的每日记账工具，帮助用户养成记录消费习惯，看清自己的收支结构。

### 2.2 平台策略：Web优先

**为什么先做网页端？**

| 维度 | 说明 |
| --- | --- |
| 成本 | 一套代码同时覆盖PC和移动浏览器，研发成本最低，验证速度最快 |
| 门槛 | 无需下载安装，打开链接即用，获客与传播成本最低 |
| 迭代 | 发版无需应用商店审核，需求验证周期短 |
| 扩展 | 数据模型与API从第一天按多端架构设计，未来APP/小程序平滑接入 |

**多端演进路线：** `网页端（V1.x）→ PWA增强（V2.0）→ APP + 小程序（V3.0）`

> ⚠️ 架构要求：账号体系、数据同步接口、分类/账单数据模型必须在V1.x阶段按"多端同步"标准设计，避免未来重构。

### 2.3 产品定位

**一句话定位：** 一款让普通人在10秒内记完一笔账的轻量级个人记账工具。

**产品理念：** 轻、快、清晰。
- **轻**：不堆砌复杂财务功能，聚焦"记"与"看"
- **快**：记账路径极短，打开即记，3步内完成
- **清晰**：数据可视化直观，一眼看懂钱花在哪
- **易**（V1.1新增）：全年龄可用，长辈也能无障碍上手

**品牌调性（V1.2新增）：** 粉嫩治愈系 —— 像一本可爱的电子手账，让记账从"任务"变成"小确幸"。详细规范见第六章《视觉设计规范》。

### 2.4 目标用户（V1.1修订：18岁以上全年龄段）

| 用户分层 | 年龄段 | 特征描述 | 核心诉求 | 对应设计策略 |
| --- | --- | --- | --- | --- |
| 青年用户 | 18-25岁 | 学生/初入职场，收入有限，手机使用重度 | 控制预算、避免月光、操作要快 | 默认交互节奏、预算提醒 |
| 中青年用户 | 26-40岁 | 上班族/家庭财务主力，收支结构复杂 | 快速记录、分类清晰、报表复盘 | 完整功能、统计图表 |
| 中老年用户 | 41-60岁 | 有余力理财，对复杂界面敏感 | 界面简单、字大、看得懂 | 大字号模式、简化术语 |
| 银发用户 | 60岁以上 | 记账习惯强（从纸质账本迁移） | 极简操作、高对比度、防误触 | 长辈模式、二次确认 |

**设计原则：一套界面，两种模式**
- **标准模式**：默认，面向18-40岁用户
- **长辈模式（关怀版）**：一键切换，字号放大1.3倍、简化页面层级、隐藏低频功能、增强色彩对比（V1.1纳入P1需求）

### 2.5 使用场景

| 场景 | 描述 | 平台 |
| --- | --- | --- |
| 场景一：即时记账 | 用户在便利店付款后，用手机浏览器打开网页记一笔"早餐 8元" | 移动H5 |
| 场景二：睡前补记 | 用户晚上花5分钟回顾当天消费，在电脑上集中补录几笔账单 | PC Web |
| 场景三：月底复盘 | 用户在电脑大屏上查看本月消费报表，分析餐饮支出是否超标 | PC Web |
| 场景四：预算控制 | 用户设置本月餐饮预算1500元，消费接近时收到提醒 | 双端 |
| 场景五：长辈记家用 | 60岁用户用平板记录每日买菜开销，替代纸质账本 | 移动H5/平板 |

## 三、需求分析

### 3.1 用户痛点

| 序号 | 痛点 | 说明 |
| --- | --- | --- |
| P1 | 记账坚持不下来 | 传统记账软件操作繁琐，记一笔要点很多步 |
| P2 | 记了也白记 | 只有流水没有统计，看不出消费结构 |
| P3 | 花钱没概念 | 不知道这个月还能花多少，经常超支 |
| P4 | 查找不方便 | 想找某笔历史消费，翻很久找不到 |
| P5（V1.1新增） | 软件太复杂学不会 | 中老年用户面对繁杂界面直接放弃 |
| P6（V1.1新增） | 不想装APP | 用户不愿为轻需求下载安装，网页即用即走 |

### 3.2 需求优先级说明

本文档采用 P0/P1/P2 三级优先级：
- **P0（必须有）**：MVP版本核心功能，缺了产品不成立
- **P1（应该有）**：显著提升体验，第二迭代加入
- **P2（锦上添花）**：增强功能，视资源情况安排

### 4.2 功能需求明细

#### 模块一：记账模块 ⭐核心

**需求编号：BR-01 | 快速记账 | 优先级：P0**

| 项目 | 内容 |
| --- | --- |
| 需求描述 | 用户进入记账页，选择支出/收入类型，输入金额，选择分类，保存完成 |
| 业务规则 | 1. 默认选中"支出"；2. 金额为必填，支持两位小数；3. 分类为必选，默认记住上次选择的分类；4. 日期默认为当天，可修改；5. 备注选填，限100字 |
| 交互要求 | 1. 移动H5端：记账页打开后唤起数字键盘（自定义键盘，非系统键盘，保证一致性）；2. PC端：金额输入框自动聚焦，支持物理键盘输入与快捷键（Enter保存、Esc关闭、T切换收支类型）；3. 从打开页面到保存成功，操作不超过3步；4. 保存成功有轻量视觉反馈（对勾动画/Toast），不阻断连续记账 |
| 验收标准 | 熟练用户单笔记账耗时 ≤ 10秒 |

**需求编号：BR-02 | 连续记账 | 优先级：P1**

| 项目 | 内容 |
| --- | --- |
| 需求描述 | 保存一笔后不清空收支类型与日期，仅清空金额和备注，方便用户连续补记 |
| 验收标准 | 补记5笔账单耗时 ≤ 60秒 |

**需求编号：BR-03 | 常用分类快捷区 | 优先级：P1**

| 项目 | 内容 |
| --- | --- |
| 需求描述 | 分类选择区按使用频率排序，高频分类前置展示 |
| 业务规则 | 系统统计近30天各分类使用次数，Top 8 展示在快捷区 |

**需求编号：BR-04 | PC端快捷记账 | 优先级：P2**

| 项目 | 内容 |
| --- | --- |
| 需求描述 | PC端支持全局快捷键唤起记账面板（如 `N` 新建账单），流水页支持行内快速编辑金额/分类 |

| 项目 | 内容 |
| --- | --- |
| 需求描述 | 用户在同一页面用**用户名 + 密码**完成注册或登录，页面提供【注册并备份】与【登录】两个按钮，动作显式分开：注册即建号并直接进入登录态，登录只校验凭据、不建号；成功后可一键把本机账单备份到云端 |
| 入口 | 1. 冷启动第3笔记账后的轻提示（流程二）；2. 我的页账号卡片（PG-11）；3. 着陆页次级入口「已有账号？登录」；4. 本机存储提示条内的「注册可备份」——四个入口共用同一页面与状态机，入口用 `mode` 指定默认动作（登录／注册），页内两个按钮随时可切 |
| 表单与校验 | 1. 用户名输入框：3–20 位，允许字母／数字／下划线／中文，禁空格与纯符号，失焦即校验；大小写不敏感（提交前统一转小写）；不要求与真实身份一致，并提示不要用全名或手机号当用户名；2. 密码 6–64 位，`type=password` + 「显示密码」切换，不做复杂度强约束（长辈用户能用住比能猜到更重要）；3. 注册态密码框默认明文显示——没有邮箱可找回，打错一次就是永久失号；4. 两项未填全或不合规时对应按钮置灰；5. 提交中按钮内联 loading，禁止重复提交；6. 只索取这两个字段，不要求邮箱／手机号／姓名 |
| 业务规则 | 1. 点【注册并备份】= 建号 + 签发登录态 + 进入迁移确认，一步完成，不再要求二次登录；用户名全局唯一，重名即注册失败；2. 点【登录】只校验凭据，用户名不存在与密码错误返回同一文案"账号或密码不对"，不给枚举留口；3. 注册接口必须如实提示"这个用户名已经有了"——否则用户无法理解失败原因；该处不可避免的枚举面由注册接口的 IP／设备频控与批量上限承担，不用"注册失败也说不清"换隐蔽性；4. 密码只在服务端做加盐哈希（argon2/bcrypt）校验，前端不保存明文与摘要；5. 连续失败的限流与锁定按用户名／IP 在服务端实现，前端只做文案兜底；6. 换用户名登录视为切换账号，需二次确认；7. 一个浏览器同时只保留一个登录态；8. 本版无自助找回（未收集邮箱／手机号），「忘记密码」给说明 + 导出CSV 与本机数据不受影响的兜底出口，绑定凭据与找回链路排在 V1.1 |
| 登录态策略 | Token 失效不打断当前操作：记账与编辑继续写本机，下次同步时静默续期；续期失败才弹登录层，且必须保留用户已输入的记账草稿 |
| 数据迁移 | 1. 本机有数据、云端为空 → 直接全量上传；2. 双方都有数据 → 弹窗对比笔数与时间范围，用户确认后合并，去重键 `id`，同键取 `updated_at` 新者；3. 迁移完成前不删除任何本机数据（可回退）；4. 中途失败保留 `sync_status=local`，下次进入自动续传，不重复上传 |
| 交互要求 | 1. 移动端全屏页／底部抽屉、PC端居中弹窗（宽420px），详见 5.5；2. 支持 Enter 提交、Esc 关闭；3. 关闭弹层即回到免登录状态，本机数据不受影响；4. 仅收集用户名，密码仅用于校验；5. 《隐私政策》由用户主动勾选确认，不得默认勾选 |
| 异常与文案 | 见 5.5 页面状态表：用户名不合规、密码长度不足、账号或密码不对、用户名已存在、提交中、迁移确认、忘记密码说明 |
| 验收标准 | 1. 从打开页面到注册或登录成功 ≤ 10秒（两步填写，无等待环节）；2. 成功率（排除密码错误与用户名重名）≥ 99%；3. 所有失败路径有明确文案与恢复出口，无静默失败，注册失败可原地改用户名重试且已填内容不丢；4. 1万笔本机账单迁移 ≤ 30秒，期间可继续记账；5. 页面 JS 错误率 ≤ 0.5% |
| 架构要求 | 1. `POST /api/v1/auth/register`（用户名唯一校验 + 建号 + 签发 Token）、`POST /api/v1/auth/login`（校验凭据换 Token，用户名不存在与密码错误一律 401 同码）、`POST /api/v1/auth/refresh`（续期）、`DELETE /api/v1/auth/session`（退出），RESTful 版本化，供 APP／小程序复用；用户名唯一性由数据库唯一索引保证，注册接口独立限流；找回密码 `POST /api/v1/auth/password/reset` 依赖邮箱／手机号绑定，排在 V1.1；2. 所有账单／分类／预算数据模型必须包含 `user_id`、`created_at`、`updated_at`、`sync_status` 字段（V1.0 即按此设计，未登录时 `user_id=local`）；3. 服务端只存密码加盐哈希与失败计数，不落明文；Access Token 2小时 + Refresh Token 30天滚动续期 |

> 💡 **产品决策说明**：V1.0方案中云端同步排在APP阶段，V1.1将其提前至Web端P1。原因：浏览器本地数据稳定性弱于APP沙盒（用户可能清理缓存、更换浏览器），若无云端备份，数据丢失风险直接伤害核心信任。**V1.0.1 进一步把登录/注册页单独从 V1.1 拆出提前交付**：V1.0 上线后第3笔记账的提示已经带来注册意愿，但没有可承接的页面，等于让最关键的数据信任漏斗空转一个迭代。本版只做"能登录 + 能把数据备份上云"，多端全量双向同步与离线冲突合并仍留在 V1.1。
>
> **为什么不用验证码**：验证码链路的实际转化卡在"等邮件"这一步，而邮件到达率与垃圾箱拦截不在产品可控范围内；同时它要额外背下发码服务、频控存储、行为验证码三套外部依赖，第7周交付不动。用户名 + 密码把页面压到两个字段，注册与登录再拆成两个按钮、共 10 个状态，仍是所有方案里最省的一档，先把"数据能备份"这件事交付；代价是没有邮箱就没有自助找回，该缺口作为已知风险记入第十一章，找回能力做成 V1.1 的独立链路。
>
> **为什么把注册与登录拆开**：注册登录合一看着少一个按钮，实际是把两种意图压进同一次点击——想登录的用户用户名打错会被静默建成新号，回到的是一个空账号，只会让人觉得"我的账不见了"，而这恰好砸的是本次改版要修的信任。拆开后【注册】负责建号、【登录】负责找回，失败文案各归各的（重名 vs 密码错），研发和测试也能逐条验收。

### 5.2 核心用户流程

**流程一：记账主流程（P0）**

```
打开网页 → 首页（流水页）→ 点击「+ 记一笔」→ 记账面板
→ 选择支出/收入（默认支出）
→ 输入金额（H5自定义数字键盘 / PC物理键盘）
→ 选择分类（默认上次使用）
→ （可选）填备注/改日期
→ 点击「保存」（或PC按Enter）→ 成功反馈 → 新账单置顶
```

**流程二：新用户冷启动流程（P0，V1.1新增）**

```
访问着陆页 → 点击「立即开始记账」→ 直接进入首页（免登录）
→ 完成第1笔记账 → 第3笔记账后弹出轻提示：
「数据仅保存在本浏览器，注册账号可云端备份永不丢失」
→ 用户选择【注册备份】→ 进入 PG-09 登录/注册页（V1.0.1 起可用）
→ 用户选择【暂不】→ 7天内不再提示，仅保留我的页账号卡片入口
```

**流程三：月度复盘流程（P0）**

```
打开网页 → 点击导航「统计」→ 默认本月视图
→ 查看总支出/剩余 → 查看分类环形图
→ 点击某分类 → 查看该分类账单明细
→ 返回 → 切换到上月对比
```

**流程四：注册登录与数据上云流程（P1，V1.0.1新增）**

```
进入 PG-09（我的页账号卡片 / 第3笔记账提示 / 着陆页登录入口）
→ 输入用户名与密码（≥6位）→ 按意图点【注册并备份】或【登录】
   ├─ 注册·用户名可用     → 建号并直接拿到登录态 → 进入数据迁移确认
   ├─ 注册·用户名已存在   → 行内提示"这个用户名已经有了，换一个或直接登录"，已填内容保留
   ├─ 登录·凭据通过       → 拉取云端笔数 → 进入数据迁移确认
   ├─ 登录·账号或密码不对 → 行内提示并清空密码，不区分用户名是否存在
   └─ 忘记密码            → 说明本版未收集邮箱、密码不可自助找回 + 导出CSV兜底，找回流程 V1.1 上线
→ 数据迁移弹窗（本机 N 笔／云端 M 笔）
   ├─ 【保留双方并合并】→ 按 id 去重、同键取 updated_at 新者
   ├─ 【先只备份本机】  → 全量上传，云端旧数据保留不覆盖
   └─ 【暂不处理】      → 保持本机数据，账号卡片显示"N 笔待上传"
→ 成功：Toast「已备份 N 笔账单」+ 卡片显示最近同步时间（埋点 EV-13）
→ 失败：本机数据原样保留并标记 sync_status=local，下次进入自动续传
```

### 5.5 登录/注册页布局描述（PG-09，V1.0.1新增）

移动端为全屏页（顶部返回 + 品牌标识），PC端为居中弹窗（宽420px）；两者共用同一套表单、文案与状态机；注册与登录也不做两个页面，共用同一组输入框，只切默认动作与按钮主次。首屏文案讲收益不讲动作——用户要的是"账单不会丢"，不是"登录"。

│ │ ········            │ │
│ └─────────────────────┘ │

│ [       登  录        ]│  ← 次按钮：只校验凭据，不建号

页面状态（研发需逐一实现，测试需逐一覆盖）：

| 状态 | 触发 | 视觉与文案 |
| --- | --- | --- |
| 默认·登录 | 打开页面（入口 `mode=login`） | 两个输入框 + 【注册并备份】【登录】；PC端用户名框自动聚焦，未填全时两个按钮都置灰 |
| 默认·注册 | 入口 `mode=register`，或点【注册并备份】前的注册态 | 同一组输入框，密码框默认明文显示，用户名框下常驻"3–20位，可用字母／数字／下划线" |
| 用户名不合规 | 失焦或提交 | 用户名框下 `#F9616C` 文案"用户名要 3–20 位，不能有空格" |
| 密码不合规 | 提交或输入中 | 密码框下提示"密码至少 6 位"，按钮保持置灰 |
| 提交中 | 点击任一按钮 | 该按钮内联 loading（注册"正在建号…"／登录"正在登录…"），禁止重复提交，输入框只读 |
| 账号或密码不对 | 登录接口返回失败 | 密码框抖动并清空，提示"账号或密码不对，再检查一下"；文案不区分用户名是否存在 |
| 用户名已存在 | 注册接口返回失败 | 用户名框下提示"这个用户名已经有了，换一个或直接登录"，已填内容全部保留 |
| 忘记密码 | 点「忘记密码？」 | 说明密码由服务端加盐哈希保存、本版未收集邮箱因此无法自助找回；给导出CSV兜底出口，找回流程 V1.1 上线 |
| 迁移确认 | 注册或登录成功且本机有数据 | 双栏对比本机／云端笔数与最近备份时间，按钮【立即备份 N 笔】【暂不处理】 |
| 已登录 | 再次进入该入口 | 不展示表单，直接显示账号卡片（PG-11 / ACC-04） |

> 视觉沿用第六章规范：主按钮 `#FF8FAB`（按压 `#F4759B`）、页面背景 `#FFFAFB`、卡片圆角16px、投影 `0 4px 16px rgba(255,143,171,0.15)`；错误色 `#F9616C` 仅用于文字与描边，不做整屏红底。关怀模式下按钮高度≥48px、字号×1.3，「忘记密码？」保持同样热区，且《隐私政策》勾选态必须同时给出文字说明而非仅勾选框。密码框的「显示密码」按钮热区同样≥44px，切换状态需带 `aria-label`。【注册并备份】用主按钮样式，【登录】用描边次按钮，两者不得同色同权重，避免用户按颜色猜动作。

## 六、视觉设计规范（V1.2新增）

### 6.1 设计调性

**关键词：粉嫩、可爱、轻盈、治愈**

产品视觉走"治愈系手账风" —— 像一本可爱的电子手账，让记账这件事从"任务"变成"小确幸"。

| 调性维度 | 要求 | 反面（避免） |
| --- | --- | --- |
| 色彩 | 粉色系为主，奶油感、低饱和 | 高饱和玫红、商务深蓝、金融土豪金 |
| 形状 | 大圆角、胶囊形按钮 | 尖锐直角、硬朗线条 |
| 质感 | 柔和投影、轻盈留白 | 厚重阴影、金属/玻璃拟物 |
| 文案 | 拟人化、有温度（"今天也记账啦～"） | 冰冷的系统腔 |

### 6.2 品牌配色方案

**主色板：**

| 角色 | 色值 | 用途 |
| --- | --- | --- |
| 品牌主色·蜜桃粉 | #FF8FAB | 主按钮、选中态、导航高亮、品牌标识 |
| 主色·按压态 | #F4759B | 按钮按压/Hover加深 |
| 主色·浅底 | #FFE5EC | 标签底色、卡片点缀、选中背景 |
| 页面背景·奶白粉 | #FFFAFB | 全局页面背景 |
| 卡片背景 | #FFFFFF | 内容卡片、弹层 |

**功能色（与粉色系调和）：**

| 角色 | 色值 | 说明 |
| --- | --- | --- |
| 支出·暖粉 | #FF6B8A | 替代传统红色，保留"注意"语义且不破坏整体调性 |
| 收入·奶绿 | #7BC8A4 | 薄荷奶绿，与粉色形成清新互补 |
| 警告·奶橙 | #FFB26B | 预算使用达80% |
| 超支·珊瑚红 | #F9616C | 预算使用达100%及以上 |
| 文字·主 | #3D3438 | 暖灰黑，比纯黑柔和 |
| 文字·次 | #A08E96 | 灰粉调辅助信息 |
| 分割线 | #F5E6EA | — |

> ⚠️ 设计红线：可爱 ≠ 低可读性。正文与金额文字对比度必须满足 WCAG AA（≥4.5:1）；粉色仅作点缀与功能色，正文不使用粉色小字。

**深色模式适配：** 背景 #241E21、卡片 #322A2E；主色明度上调至 #FFA5BC；功能色同步提亮一档，保持粉嫩观感与对比度。

### 6.3 字体规范

| 项 | 规格 |
| --- | --- |
| 中文字体 | 系统默认（PingFang SC / 系统黑体），字重 常规400 / 中黑500 |
| 数字字体 | 圆润风格（如 Baloo 2 / Quicksand），金额展示保持等宽，禁止错位 |
| 字号梯度（标准模式） | 页面标题20px / 卡片标题16px / 正文14px / 辅助说明12px / 首页金额大字32px |
| 关怀模式 | 整体放大×1.3，金额≥28px（详见 CARE-01） |

### 6.4 组件风格

| 组件 | 规格 |
| --- | --- |
| 圆角 | 卡片16px、按钮胶囊形（全圆角）、输入框12px、标签8px |
| 阴影 | 柔和粉色投影，示例：0 4px 16px rgba(255,143,171,0.15) |
| 图标 | 圆润粗线风格（线宽≥2px、端点圆角）；分类图标采用软萌插画风（SVG，兼容跨端复用） |
| 插画 | 扁平可爱风空态插画（小动物、存钱罐等元素） |
| IP形象（P2） | 记账小助手吉祥物（暂定名"桃桃"），用于空态引导、鼓励文案、节日皮肤 |

### 6.5 动效风格

- 基调：Q弹轻快，弹簧曲线（spring），常规动效 200-300ms
- 记账成功：金额区弹出"小心心/撒花"微动画（≤600ms，不阻断连续记账）
- 预算达标彩蛋（P2）：当月未超支时，统计页出现庆祝动画

### 6.6 与"全年龄定位"的兼容策略

粉嫩可爱是默认皮肤，但不能成为非目标审美用户的使用门槛：

1. **色彩克制**：页面大面积使用奶白底色，粉色仅作点缀与功能色，避免"整屏粉红"的压迫感
2. **关怀模式**：字号放大、层级简化，但沿用同一套配色体系（保持品牌一致性）
3. **多主题预留（P2）**：主题系统纳入V2.0规划，后续提供"抹茶绿""清爽蓝"等备选，粉嫩为默认主题
4. **文案分层**：可爱语气仅用于空态/鼓励文案；核心功能文案（按钮、标签、提示）保持清晰直白

| V2.0 | **Web + PWA** | 第16-19周 | PWA改造（添加到主屏幕、离线可用、接近APP体验）、年度财务报告、分享卡片、多主题切换（粉嫩默认 + 抹茶绿/清爽蓝备选） | 补齐Web端留存短板 |
| V3.0 | **APP + 小程序** | 第20周起 | iOS/Android APP（可基于PWA或跨端框架）、微信小程序（复用现有API与数据体系）、多端实时同步打通 | 全平台覆盖 |

**V1.0 范围外明确不做（Out of Scope）：**
- ❌ 多人共享账本 / AA记账
- ❌ 自动同步银行卡/支付平台账单（涉及合规与安全，后续单独评估）
- ❌ 理财产品推荐、社区内容
- ❌ 广告位
- ❌ V1.0不做账号体系（V1.0.1 加入登录/注册页与备份上云，V1.1 加入多端双向同步）——但数据模型必须预留
- ❌ V1.0.1不做：第三方登录（微信／Apple）、手机号登录、密码登录、付费会员、多设备实时协同编辑、端到端加密

**跨平台架构要求（为V3.0铺路）：**
1. 后端API从V1.0.1起采用RESTful规范、版本化（/api/v1/，首批为 `/api/v1/auth/*`），供Web/APP/小程序复用
2. 数据模型预留 `platform` 字段标记来源端
3. 分类图标等静态资源使用统一的跨端图标库（SVG）

## 十一、风险与依赖（V1.1修订）

| 类型 | 内容 | 应对策略 |
| --- | --- | --- |
| 产品风险 | 记账类产品普遍留存低，用户易流失 | MVP聚焦"快"这一核心差异点；用统计价值反哺记账动力；V1.2加入提醒功能 |
| 平台风险（V1.1新增） | Web端无桌面图标、无强通知能力，留存天然弱于APP | 引导收藏/添加到主屏幕；V2.0 PWA改造提前储备；V1.1 绑定邮箱后邮件提醒作为替代触达；V3.0尽快补APP/小程序 |
| 数据风险（V1.1新增） | 免登录模式下用户清浏览器数据导致账单丢失 | V1.0.1 交付登录与一键备份（ACC-02）从根上收敛该风险；过渡期靠第3笔记账强引导 + 一键导出CSV兜底；着陆页与设置页双重提示 |
| 用户风险（V1.1新增） | 全年龄段用户数字素养差异大，中老年用户可能流失于学习成本 | 关怀模式 + 术语通俗化；着陆页提供30秒视频演示；核心路径埋点监控各年龄段漏斗 |
| 视觉风险（V1.2新增） | 粉嫩可爱风格存在审美偏好分化，可能降低部分用户（如中老年男性）的接受度 | 大面积奶白底+粉色点缀，控制粉色占比；V2.0提供多主题；关键信息不单纯依赖色彩传达 |
| 交付风险（V1.0.1新增） | 登录页依赖后端账号服务，若后端排期晚于第7周，页面会空转；纯前端版本无法自测登录态 | 1. 前端先按 5.5 状态机完成页面并以 mock 联调；2. 账号服务（建号／校验／Token／限流）第6周前完成接口约定；3. 后端延期时的降级包（只强化导出备份 + 保留登录入口）必须走评审确认，不得静默降级 |
| 安全风险（V1.0.1新增） | 密码体系带来拖库撞库与暴力尝试风险；用户复用其他网站密码造成连带泄露；用户名全局唯一使注册接口天然可被用来探测某个用户名是否存在 | 服务端 argon2id 加盐哈希 + 用户名／IP 双维度限流与递增退避 + 连续失败锁定（ACC-02）；登录统一"账号或密码不对"文案，注册侧的重名提示按 IP／设备频控与批量上限抬高枚举成本；不做密码复杂度加码，但在密码框下提示"不要用其他网站同款密码"；保留导出CSV的兜底路径 |
| 账号找回风险（V1.0.1新增） | 只收用户名、不收邮箱与手机号，密码一旦忘记就没有自助找回通道，用户会永久失去云端账单——这是本次口径调整换来的最大代价 | 1. 注册态密码框默认明文 + 注册成功 Toast 强调"用户名和密码是找回账号的唯一凭据"，压低打错与遗忘概率；2. 「忘记密码」给导出CSV与"本机账单不受影响"的说明，保证不会二次受损；3. V1.1 交付绑定邮箱／手机号的 `POST /api/v1/auth/password/reset`；4. 人工核身找回待 V1.1 评估，本版不做承诺 |
| 技术风险 | 大数据量下统计图表性能 | 统计结果预计算缓存；图表库选型支持虚拟渲染（如 ECharts） |
| 合规风险 | 涉及个人财务数据；用户名虽不直接构成个人身份识别信息，仍属个人信息范畴，收集须告知同意并保障删除权 | 数据加密存储与传输；隐私政策明示数据用途；登录页由用户主动勾选《隐私政策》；提供账号注销与7天冷静期彻底删除出口（ACC-04） |
| 依赖项 | 技术选型：前端框架（如 React/Vue）、图表库（如 ECharts）、本地存储（IndexedDB封装库）、后端与数据库方案；**（V1.0.1新增）账号服务 `/api/v1/auth/*`（用户名唯一索引、密码加盐哈希、注册与登录两个接口的限流与 Token 签发）、失败计数存储（Redis 类）；邮件／短信发送服务（找回密码用，V1.1，本版无触达依赖）** | 研发在MVP启动前完成技术选型评审，选型需同时满足未来APP/小程序复用；V1.0.1 所需账号服务须在开发第6周前完成接口约定与压测，邮件服务的域名与配额申请可放到 V1.1 启动前 |
